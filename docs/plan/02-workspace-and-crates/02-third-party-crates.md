# 02.02 — Third-party crates

What we use, for what, in which of our crates, and the alternative we didn't pick.
**Pin exact versions at implementation time** (check crates.io for the current
release). The versions below are only the major line.

---

## Runtime and async

| Crate | For | Used in | Notes |
|---|---|---|---|
| `tokio` (1.x) | async runtime, tasks, channels, timers, `spawn_blocking` | sync, app, api, server, store-terminus | P1. |
| `tokio-util` | `CancellationToken` (stop a sync cleanly) | sync, server | |
| `futures` | `Stream`, `join_all`, `buffer_unordered` | sync, api | `buffer_unordered(n)` is how we cap concurrency without a semaphore. |
| `tokio-stream` | `BroadcastStream` (turn a broadcast receiver into a `Stream` for gRPC) | api | |
| `dashmap` (maybe) | concurrent map of open projects | app | a `RwLock<HashMap>` is fine too; pick one |
| `rayon` | CPU-parallel loops (hashing files, pylspt fan-out) | sync, drivers | Data parallelism on threads. Never call rayon from *inside* a tokio task directly; go through `spawn_blocking` or a channel. |

> **🦀 Rust note: channels you'll use.**
> - `tokio::sync::mpsc`: many senders, one receiver. Watcher → scheduler.
> - `tokio::sync::oneshot`: a single reply. "Run this sync, tell me when done."
> - `tokio::sync::broadcast`: one sender, many receivers that each get every message. Progress events → every UI stream.
> - `tokio::sync::watch`: receivers see only the **latest** value. "Current sync status" for late subscribers.
>
> Choosing the right channel removes most locking: instead of sharing state behind a
> `Mutex`, one task *owns* the state and others send it messages. This is the
> **actor pattern**, and the scheduler and the pylspt db owner both use it.

## Deliberately **not** used

| Not using | Why |
|---|---|
| An ORM | No ORM speaks TerminusDB, and our repos are thin anyway. |
| `async-trait` **everywhere** | Rust ≥ 1.75 has native `async fn` in traits. We use the `async-trait` macro **only** on the few traits we need as `dyn Trait` (store, driver, id strategy), where it's the simplest working option. Explained in 03-storage/01. |
| `socket.io` server (`socketioxide`) | D3 chose gRPC; progress uses gRPC server-streaming. |
| A JSON-RPC framework (`jsonrpsee`) | The driver protocol is a few methods over HTTP POST; `reqwest` + 30 lines is clearer. (Same conclusion as `pylspt/plan/04-build/03-transport-and-parity.md`.) |
