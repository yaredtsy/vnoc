## 1. What it ships

Open a function's code on its card, press **Edit**, type, press **⌘S**. The function in the file now has the new text. The tree, the doc badges
and the call trees follow after the save, as they do today when you save in a normal editor.

| In | Out (later) |
|---|---|
| editing one function, class or file slice in its card | a live view: the card and an editor tab showing each other's typing |
| ⌘S in the card writes it into the file | the outline, ranges or call trees following unsaved text |
| a function that was changed in the editor is never overwritten | undo that spans the card and the tab |
| editing a doc in the doc panel, by the same rule (§8) | syntax errors under the cursor while typing |

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| **E1** | **The card edits a draft.** Nothing leaves the card until ⌘S. | Nothing to send per keystroke, so nothing re-runs, and no edit bounces back and forth between the card and VS Code's document. |
| **E2** | **The index follows saves only**, as now (`extension/src/core.ts:172`, the file watcher). No outline, range or call tree of unsaved text. | Following unsaved text means a re-outline, moved ranges and a new call tree on every keystroke. |
| **E3** | **Save checks before it writes:** the document's version, then the function's text against the draft's starting text (§6). A function changed in the editor is never overwritten. | One check replaces a live view. |
| **E4** | **Save writes through a `WorkspaceEdit`, then saves the file only if it was not dirty before**: the rule `relink.ts`, `addDoc.ts` and `writeId.ts` already follow. | Unsaved work of the user's own in a tab is never saved for them. |
| **E5** | **Editing a file that has unsaved changes is refused**: "Save `<file>` first", with a **Save and Edit** button. | The card's range comes from the last save. In a dirty file it can point at the wrong lines (§5). |
| **E6** | **A draft lives in the webview** (a store beside `webview/src/state/view.ts`, saved with the same `vscode.setState` call: `setState` keeps one object per webview, so the draft must go into `view.ts`'s `Saved`, not a second call that would overwrite it), not in the extension. | The panel already has `retainContextWhenHidden`, so hiding the tab keeps the draft; `setState` keeps it through a webview reload. The page is the owner of the drafts; the extension holds only a copy (below). Measured in 9.0 (check C): 100 KB and 1 MB survive hiding the tab and *Developer: Reload Webviews*, and one `setState` call takes about 1 ms at either size. **A `setState` that is not `view.ts`'s own is dropped within seconds**: its subscriber writes its own object at the first view change, even a hover, and `probe` was gone in under 2 s with nothing touched. That is why the draft goes into `Saved`. **The extension holds a copy of the drafts, fed by the page; it acts on it only when the canvas is closed or at start** (9.5c). **Why:** a webview panel can't be dirty and can't veto its own close, so VS Code cannot ask before it closes the canvas, and closing the tab destroys the page and its `getState` with it (measured, §7). The copy lets the host ask right after the close, so nothing is lost. **How it is fed and cleared:** the page posts the whole list as a note `drafts`, at once on any change of a draft's state (start, `saving`, `conflict`, `gone`, Discard, dropped after a save) and 500 ms after the last keystroke for typing (`text`), and at once when the page is hidden (`visibilitychange`) or leaves (`pagehide`), as best-effort flushes of a pending debounce. The host replaces its copy each time, in memory and in `workspaceState` (`vnoc.drafts`); an empty list clears it. A canvas page that starts asks once with the request `drafts` (as it asks for `dirtyFiles`): its own `setState` drafts win if it has any (a webview reload keeps them; it then tells the host), else it takes the host's copy, each draft in its saved state (`saving` comes back `editing`). The page and the host share one `Draft` type, `shared/messages.ts`; the rules (which drafts count, what each notification says, what Save All leaves) are `shared/drafts.ts`. |
| **E7** | **The live view (S5's first question) is later**, and it is not a format change. | Nothing on disk depends on how the card edits. |

## 3. Why a draft, not a live view

The 0.3 row in `02` said "Monaco as a view of VS Code's document". That means two copies of the text kept equal on every keystroke, in both
directions. It brings in:

- **edits that bounce**: the card writes to the document, the document's change event comes back to the card, the card applies it again;
- **range tracking**: the function's range moves with every edit above it, and the card has to move it too, without the driver;
- **re-runs**: everything that hangs on a range (badges, Missing, calls) would want to follow, or show stale results.

A draft has none of these. Its one cost is that the card and an open tab do not see each other's unsaved typing, and §6's check makes that safe.

## 4. A draft: its states

```
reading ──Edit──► editing ──⌘S──► saving ──ok──► reading (the new text, after the index updates)
   ▲                 │               │
   │                 │               ├──changed in the editor──► conflict ──Reload──► editing (new start)
   │                 │               │                               └────Show Diff──► a diff tab
   └──Discard────────┘               └──the function is gone──────► gone ("open in editor")
```

| State | The card shows |
|---|---|
| reading | today's read-only Monaco. A dot and "unsaved in editor" in one line above the code (the code area, not the header) when the file has unsaved changes (today the slice can be wrong then, unmarked) |
| editing | Monaco writable, a dirty dot when the text differs from the start, **Save** and **Discard** in the card's header (below) |
| saving | the same, disabled, for the time one request takes |
| conflict | "Changed in the editor since you started": **Reload** (keep nothing), **Show Diff** (the draft against the file) |
| gone | "Not found in `<file>` any more": **Open in Editor**, **Copy Draft** |

A card that leaves the screen (its parent collapsed, scrolled away, its code hidden) keeps its draft: the store keeps it, so there is no question (decided 2026-11-16, 9.5). What can be lost is the canvas itself closing: §7.

**The header's buttons by state** (decided 2026-11-16; the header is `16-ui-redesign/04-node-cards.md` §3):

| The card | Header buttons |
|---|---|
| code closed | Focus · Go to Code · `</>` · Add Doc (unchanged) |
| code open, reading | Focus · Go to Code · `</>` · **Edit** · Add Doc |
| editing | Focus · Go to Code · **Save** · **Discard** · Add Doc |
| saving | `editing`'s buttons with **Save** and **Discard** disabled |
| conflict, gone | `editing`'s buttons with **Save** disabled |

**Call cards edit their callee** (decided 2026-11-16). A call card has `</>` today, so in reading it gets **Edit** too: Explore · Go to Code · `</>` · **Edit**. While editing it shows Explore · Go to Code · **Save** · **Discard** (the same states as the table: `saving` disables both, `conflict` disables Save). The draft is keyed by the callee's key, not by the card, so 9.5's one-draft-per-node rule covers a structure card and a call card on the same function. A card with a code slot is a class or function card with a range, or a call card whose callee is known and has a range. A file card has none (below, §7).

- Nothing appears, moves or hides on hover (`04` §3): the buttons change with the card's state only, and **Save** stays in the same place for the whole edit. It is disabled while the draft equals `base` and enabled once the draft differs. The dirty dot before the name shows at the same time.
- `</>` and **Edit** give their two slots to **Save** and **Discard**, so the code cannot be closed with its button in the middle of a draft. Closing the card still asks Save / Discard / Cancel.
- Codicons: `edit`, `save`, `discard`. A tooltip names the key where there is one: "Save (⌘S)".
- The footer has no Save or Discard. The conflict and gone states keep their buttons (**Reload**, **Show Diff**; **Open in Editor**, **Copy Draft**) in the card's body.
- With the code open in the reading state the header holds five buttons, and a name gets about 11 characters instead of 14.

## 5. Opening a draft

**Edit** on the card (the header's button, `cardButtons.ts`; and on the node menu, `16-ui-redesign/08`: the entry `vnoc.editInCard` in `4_code` after Go to Code, on a function, a class or a call card with a known callee, on the canvas only) does this:

1. The webview asks the host `editStart { path, range }`.
2. The host opens the document. **If it is dirty, it answers `{ dirty: true }`** and the card shows E5's message. **Save and Edit** saves the
   document and starts again from 1; the save makes the index update, so the range is fresh.
3. Otherwise the host answers `{ text, version, prefix }`:
   - `text`: the range's text, as `codeOf` reads it today (`extension/src/commands.ts:383`);
   - `version`: `document.version`;
   - `prefix`: the text of the first line **before** `range.start` (the `def`'s indentation, tabs or spaces as written).
4. The card keeps `{ key, path, range, version, base: text, prefix }` and shows the text dedented, as today (`NodeCode.tsx`, `dedent`).

**While a card has a draft it never reads its code again** (decided 2026-11-16). In reading, `NodeCode` reads again on a new range and on a flip of its file's dirty state (9.1). In `editing`, `saving`, `conflict` and `gone` it keeps the draft and the draft's own `{ path, range, version, base, prefix }`, whatever the index or the tab does: a change under it is found at save time, by §6's checks, not by moving the draft. Discard drops the draft, and the card reads again, as in reading.

## 6. Saving a draft

The webview sends `editSave { key, path, range, version, base, prefix, text }`. Everything below runs in the extension.

### The three cases

| Case | What the host does |
|---|---|
| **the document's version is still `version`** | write `text` at `range` |
| **the version changed, and the function's text still equals `base`** (an edit elsewhere in the file) | ask the core where the node is now: `vnoc/locate` (below). Write at the new range |
| **the version changed, and the function's text differs from `base`**, or `vnoc/locate` finds it with different text | answer `{ conflict: true }`; write nothing |
| `vnoc/locate` finds no such node | answer `{ gone: true }`; write nothing |

**`vnoc/locate { key, document }` → `{ range } | null`**, a new core method. `document` is the `{ uri, version, text }` that `vnoc/attach`
and `vnoc/writeId` already take. The core outlines that text (the driver's `vnoc/outline` already accepts `text`, `06-drivers.md` §2) and finds
the node with that key, by ID first, then by qualname, as `identity/resolve.rs` does. It is **one driver call per save**, and only in the second
row. Nothing is cached.

In the second row the host reads the text at the new range and compares it with `base` before it writes. A match by qualname whose text changed
is the third row, not the second.

### Putting the indent back

The card shows the text with the first line's indent taken off the other lines (`dedent`, for display, `shared/indent.ts`). On save the host writes `reindent(draftText, base, prefix, eol)` (the same file, so it runs in the extension). It writes each line of the draft like this (decided 2026-11-16, 9.3a):

- **A line that matches a line of `dedent(base)`** is written as **the base's own line, byte for byte**: its indent, its trailing whitespace, a docstring line at the margin. The match is a line diff, a longest common subsequence run after the lines the two share at the start and at the end are matched without looking, so an edit in the middle of a big class costs the size of the edit. (More than 4 million cells between the common head and tail, and nothing in between is matched: it is written as new text.)
- **A line the user added or changed** is `prefix + line`; an empty line stays empty. The first line goes in as it is (the range starts after `prefix`), and it is matched only with the base's first line.
- Lines are split on `\n` and `\r\n` and joined with the document's `eol`. `editStart` returns it (`document.eol`) beside `text`, `version` and `prefix`, and the draft keeps it; a draft saved before it was there has `"\n"`.

So **saving a draft that was not changed gives back the same bytes, always**: blank lines, whitespace-only lines, margin lines and CRLF files included. What is not given back: a line ending that differs from the document's (a file with mixed endings gets the document's one on every line it writes), and **one leftover**, an edited line that sat at the margin or had less indent than `prefix`, which gains `prefix`. It was typed on, so this is accepted.

### Writing it

**The check is ours** (step 9.0, check B). A plain `WorkspaceEdit` carries no document version, and `vscode.workspace.applyEdit` applies it even after the document changed: with a line added at the top, an edit at the old range returned `true` and replaced the wrong lines. VS Code does no version check. The only one in the product is the language client's, for the core's `workspace/applyEdit` (`vscode-languageclient` 9.0.1, `lib/common/client.js:1457`; its converter drops the version from the edit), and it protects only the core's edits (`vnoc/attach`, `vnoc/writeId`, relink). `editSave` is the first extension-side text write, so the version and `base` checks of the table above are written in our code.

1. Read `document.version` and the text at the range. Choose the row of the table from those two. **No `await` between that read and the call to `applyEdit`**: any await lets the document move on, and nothing after it would notice.
2. `wasDirty = document.isDirty` (false, by E5, unless the user typed in the tab since the draft started).
3. A `WorkspaceEdit` that replaces the range with the re-indented text. If `applyEdit` returns false, answer `{ conflict: true }`.
4. If `!wasDirty`, `document.save()`. The watcher sends `vnoc/filesChanged`; the index updates; the card gets its new range with the next
   structure, as any card does after a save.
5. If `wasDirty`, the text is in the editor's buffer but not on disk. The card says "Written into `<file>`, not saved". **The card does not wait for the index** (decided 2026-11-16, 9.4): nothing was saved, so it will not move. The draft is dropped at once, and the card reads its code and shows "unsaved in editor" (9.1); the index follows when the user saves the tab.

**The `vnoc/locate` await (decided 2026-11-16).** The second row awaits `vnoc/locate`, and the document can change during that await. After it answers, read `document.version` again. If it is not the version the core was given, answer `{ conflict: true }`. Otherwise choose the row again, with no `await` before `applyEdit`, as step 1 says. One `applyEdit` round trip stays open (the edit is applied in the main thread after our call, and nothing of ours can close that): accepted. 9.4 pins the rule without a race: the save logic takes `locate` as a parameter, and a window test (§11 g) passes a fake `locate` that edits the document before it answers. It expects a conflict and the file unchanged.

**Already saved beats conflict** (decided 2026-11-16, 9.4). Before the host answers `conflict`, in any row, it checks whether the text at the range it is looking at (the draft's own, or where `vnoc/locate` found the function) equals what Save would write, `reindent(text, base, prefix, eol)`. If it does, it answers `saved` (or `written` if the document is dirty) and **writes nothing**. This covers a second Save of the same draft, and a draft that was `saving` when the page reloaded and whose write had landed. The order is, in `extension/src/saveDraft.ts`: `firstStep` (the version is the draft's: write, already saved or conflict; else locate), then `afterLocate` (gone, conflict if the version moved while the core looked, write, already saved, conflict). The one answer it cannot give is for a draft that renamed a function with no ID in the code: the key no longer names anything, and a second Save answers `gone`.

## 7. Edge cases

| Case | What happens |
|---|---|
| the draft deletes or changes the `ID:` line | **Built (9.5b).** In the row that writes, before the write, the host checks whether `base` has an `ID:` value the re-indented text does not have anywhere (`shared/idLine.ts`, `dropsId`). If so it asks, in a modal: "This removes `<name>`'s ID: its docs will be Missing." **Save Anyway** / Cancel (`editSaveOf`'s parameter `ask`). Cancel answers `{ cancelled: true }`: the draft goes back to `editing`, nothing is written. After Save Anyway the save goes through its rows from the top again (the document may have moved while the question was open), without asking a second time. After a save, the existing "ID was removed" flow takes over (`11-missing-relink-remove.md`) |
| the draft renames the function, or splits it into two | written as any edit. After the save the node is found by ID if it has one, else it goes Missing as after a rename in the editor. The card follows the ID, or shows "gone" |
| the file was deleted or renamed while the draft was open | `openTextDocument` fails, or `vnoc/locate` finds nothing: gone |
| two cards on the same function | **Built (9.5a).** The second **Edit** is refused: the card says "Already being edited in another card" (above the code, until that draft is saved or discarded), and the card that holds the draft is revealed with the session's `reveal`, as a sidebar click does: its parents open so it is drawn, the canvas centres on it. `reveal` takes a call id too (the owner function opens and the call cards above it; nothing is selected, because selecting a call card follows it into a preview EXPLORE). The rule is `editBlock` in `draftRules.ts` |
| the same file in two cards (two functions) | each draft is its own range. The first save changes the version, so the second save takes the second row of §6, one `vnoc/locate` |
| ⌘S when the focus is in the card | **Decided (9.0, check A).** While the card is `editing`, a `keydown` listener on the card's container (bubble phase) calls `stopPropagation()` for ⌘S, ⌘⌥S and ⌘⇧S, and for no other key. Monaco's `addCommand(CtrlCmd + S)` runs first and saves the draft. ⌘⌥S in the card saves the draft only. ⌘⇧S does nothing. **Windows and Linux (decided, not tried):** the same with Ctrl: the card swallows Ctrl+S and Ctrl+Shift+S while editing. Ctrl+K S (Save All) is a chord whose first key must reach VS Code, so it is not swallowed: VS Code saves its dirty files, and the draft, which is not a file, stays in the card, unsaved. Accepted. Every other key passes, so ⌘P, ⌘W, ⌘B… still reach VS Code with the focus in the card. Which keys a card swallows, by edit state, is a pure function next to the card with a table test (9.2, §11 f). `preventDefault()` alone does not stop VS Code (measured; §10) |
| a card leaves the screen with a draft | nothing: the draft stays in the store, and the bar's "N unsaved drafts" still counts it (decided 2026-11-16, 9.5). There is no close question |
| the canvas is closed with a draft | **Built (9.5c).** The page is gone and so is its `getState`, but the host has a copy (E6). If drafts count (changed, or in `conflict` or `gone`), a notification at once: "N unsaved draft(s) from the canvas", **Save All** / **Reopen Canvas** / **Discard**. *Save All*: each draft goes through `editSaveOf`, every row, the ID question included; `saved` and `written` leave the copy, a `conflict` or `gone` stays in that state, and a second notification says "K could not be saved: Reopen Canvas to see them" with **Reopen Canvas**. *Reopen Canvas*: opens the canvas, which asks for the drafts and gets them in their states. *Discard*: clears the copy. *Dismissed or ignored*: the copy stays, and the drafts come back the next time the canvas opens. If nothing counts (an Edit nothing was typed into) there is no question and the copy is cleared |
| the window reloads or closes with a draft | A canvas tab that VS Code restores gets its drafts from its own `setState` (the serializer, below). At the extension's start (1.5 s after activation), if the copy has drafts that count and no canvas is open or waiting as a tab: "N unsaved draft(s) from the canvas", **Reopen Canvas** / **Discard** (no Save All: a window that has just opened has not read the code). The host cannot ask before a window closes: the copy, written as the page fed it, is what the next window finds |
| a file and a folder card | **file: later; folder: never** (decided 2026-11-16). A file card has no `</>` (`cardButtons.ts`: code in the card is for a definition with a range), so it has no code to edit and no **Edit**. A folder has no code at all |

**The close check (2026-11-16, before 9.5a; it is why 9.5c exists).** *Closing the canvas tab loses the drafts today: measured.* A draft with typed text was started, the tab was closed (not hidden) and the canvas opened again: the new page's `vscode.getState()` was `undefined` (a throwaway note from the page, removed), and no card said `editing`. Closing destroys the webview and its state; `retainContextWhenHidden` covers hiding only. *The canvas has a `WebviewPanelSerializer`* (`extension.ts`, `registerWebviewPanelSerializer(CANVAS, …)`, activation event `onWebviewPanel:vnoc.canvas`), which serves a canvas tab that was open when the window was reloaded or restarted; its `restore` takes the panel and ignores the `state` argument, because the page reads its own `vscode.getState()` (the drafts are in `Saved`, E6). A tab that was closed has nothing to restore. *Developer: Reload Window: not measured.* It was tried in the window suite: the reload ends the run (VS Code exits with the extension host) before the restored page can say anything. What is known: *Reload Webviews* keeps the state (9.0, check C), and VS Code keeps a panel's state across a reload when a serializer restores the panel. By hand, in §10's list for 9.5.

## 8. The doc panel: the same rule for Markdown

F7 (`08-decisions-to-log.md`) moved editing a doc inside the panel to this plan. It uses the same draft, with the whole file as the range.

**Decided 2026-11-16 (before 9.6).**

| # | Decision |
|---|---|
| 1 | **Both surfaces edit**: the canvas's docs panel and the docs tab, because both are `DocPanel` (the docs tab is `DocPanel` with `fill`). One implementation. |
| 2 | **A doc draft is a whole-file draft.** Its range is the whole file, its `prefix` is `""`. Save goes through the same `editSaveOf` rows, with a `locate` that answers the current document's whole range (`docLocate`), so the version check, the "text equals `base`" row, conflict, "already saved" and `written` all apply unchanged. **Gone** is the `.md` deleted or renamed: `openTextDocument` fails. No ID question for a `.md` (a Markdown file has no `ID:` line). `reindent` with an empty prefix gives the text back byte for byte, `eol` honoured (`shared/indent.test.ts` has the Markdown rows). |
| 3 | **One draft per doc, across both pages.** The canvas and the docs tab are separate pages that cannot see each other, so the rule lives in the host. The docs tab's page feeds its drafts the way the canvas does since 9.5c, and the note is tagged with the page (`canvas` or `docs`); the host's copy is one list per page. `editStart` for a doc the *other* page has a draft of answers `{ busy: true }`, and the panel says "Already being edited in the canvas" (or "in the docs tab"), with no reveal across pages. |
| 4 | **The panel's buttons.** Reading: **Edit** (the pencil, in place) and **Open in Editor** (`go-to-file`: the `.md` in a tab, as the pencil did before 9.6). Editing: **Save** · **Discard**, with the same disabled rules and tooltips as the card (§4). The conflict and gone states have a card's lines and buttons: Reload, Show Diff; Open in Editor, Copy Draft. The buttons and the lines come from pure functions, reused or shared with the card's where they are the same. |
| 5 | **The editor** is Monaco with `language: "markdown"` and the card's options (`editContext: false`, `nokey`, the key rules of 9.2c and 9.2d, the save keys of §7). It fills the panel's body in place of the rendered Markdown. The frontmatter is shown and edited as text. |
| 6 | **After a save** the panel shows the rendered doc again, from the `docText` event. There is no index wait for a doc, so the draft drops at once. |
| 7 | **E5:** a `.md` dirty in a tab refuses Edit: "Save `<file>` first" with **Save and Edit**. There is no range to refresh after the save, so Save and Edit starts at once. |
| 8 | **Closing:** a docs tab closed with a doc draft gets 9.5c's notification, generalised: "N unsaved draft(s) from the canvas", "… from the docs tab", or "… from V-NOC" (both). **Reopen** reopens the page those drafts came from. |
| 9 | **The frontmatter: check, don't decide.** Whether editing a frontmatter line can detach a doc from its node was checked in the core in 9.6b: it cannot (the finding and a proposal are below, as a gap). Nothing is built for it. |

**Built, 9.6a (the host side).**

- **`kind: "doc"`, not a path rule.** `editStart`, `editSave` and `editDiff` take `kind: "doc"` and the Markdown file's absolute path (`DocInfo.path`). A path rule would have to tell an absolute `.vnoc/` path from a relative code path, and when the git root is the opened folder a doc's path is also a path "below the opened folder", so one string would mean two things. `Docs.resolve` checks it exactly as the panel's reads are checked: inside `<git root>/.vnoc/nodes/`, a `.md`. A draft of a doc has `Draft.kind = "doc"`, its `key` and `path` are the file's path, its `range` is the whole file, and its `card` is the node the panel showed it for.
- **`editStart` for a doc** answers `{ text, version, prefix: "", eol, range }` with the whole file as the range (`wholeRange`: lines counted as VS Code counts them), `{ dirty: true }` for a file with unsaved changes, or `{ busy: true }`. With `saveFirst` it saves the file and answers at once.
- **`busy`** is `busyWith` (`shared/drafts.ts`): the other page has a draft of this doc *and that page is open* (a panel, or a restored tab). A canvas closed with a draft the user has not yet answered for still holds it in the copy, but nobody is editing it, so the docs tab may. The copy learns a page's drafts from its note, so a second `editStart` that arrives before the first page's note has been read could pass both: a few milliseconds, accepted.
- **The copy is one list per page** (`workspaceState` `vnoc.drafts` is `{ canvas, docs }`; the plain list of 9.5c is read as the canvas's). A page that is closed asks about its own drafts only; at start one notification speaks for every page that has drafts that count and is not open (`sourceOf`), and Reopen brings back each of them. The notification names the page (`closeNotice(n, from)`), and so do the second notification and the buttons (`Reopen Canvas`, `Reopen Docs Tab`, `Reopen`).
- **Gone.** A `.md` that cannot be opened answers `{ gone: true }` (§7: the file was deleted or renamed); a path that is not a V-NOC doc is an error, not "gone".

**Built, 9.6b (the panel).**

- **One component, two pages.** `DocPanel` has the reading, editing, saving, conflict and gone states. The buttons are `docButtons` and the line above the editor is `docLine` (`webview/src/docs/docEdit.ts`, pure, with table tests); the buttons' disabled rules are the card's, and the lines are the card's own components, which moved to `node-card/DraftLines.tsx`. The editor is the card's Monaco, which moved to `node-card/CodeEditor.tsx` unchanged (a `language` prop was added), with the Markdown grammar added to Shiki. A doc's draft starts with `beginDocEdit` and goes through the card's `saveDraft`, `discardDraft`, `showDiff`, `openInEditor` and `copyDraft`: `kind: "doc"` is the only difference (a doc waits for no index, so the draft drops as soon as the host has written it, and the panel asks for the text again).
- **The draft's identity.** `Draft.key` and `Draft.path` are the `.md`'s path; `Draft.card` is the node the panel showed it for, so a page can bring it back; the marks of a doc (the refusal, the busy line, the notice) are kept by the path (`markKey`). `newDocDraft` is the pure start.
- **A doc with a draft is the doc shown.** The panel shows the doc that has a draft before the one chosen, and the doc selector is disabled while there is one, so a switch of doc or of node cannot hide a draft. On the docs tab the tab pins itself to the draft's node (`DocsApp`), and the pin toggle is disabled while there is a draft: a cursor move would otherwise take the tab away from it. On the canvas the bar's chip counts a doc draft like any other, and its click opens the panel and reveals the draft's node.
- **Coming back.** The docs tab's page feeds the host as the canvas does (`state/draftFeed.ts`, tagged by `state/page.ts`) and asks for its drafts when it starts. A canvas that takes a doc draft from the host opens the doc panel and reveals the node; a docs tab takes it and pins itself to the node. Tested: the docs tab closed with a draft, "1 unsaved draft from the docs tab" with Save All / Reopen Docs Tab / Discard, and Reopen brings the draft back, which Save then writes.
- **Gaps, decided:** (a) **a refusal for a dirty `.md` stays until Edit is asked again** (or Save and Edit is pressed). For a function the card learns when its file is saved from the set of dirty files, which is relative to the opened folder; a doc lives under `.vnoc/` at the git root, which may be above it, and the page is not told. The same goes for the line "Already being edited in the canvas": the other page's draft going away is not told to this one, and Edit asks again. (b) Both pages open on one doc: the first Edit wins and the second page says so; there is no handover. (c) A doc's `eol` is the document's. A file with mixed endings gets that one on every line it writes: the same limit as a function's (§6). (d) The suite's `docEdit`, `docSetDraft`, `docSave` and `showDocPanel` are `viewCommand`s (the key of a doc command is the doc's path), and the docs tab is driven with the real command `vnoc.showDocs`.
- **Not measured, by hand:** how the panel looks with the editor and the line (§10's list for 9.6), and ⌘S, ⌘P and Space in the editor in the docs tab. The key rules are the card's, and the docs tab is the one place they run outside a canvas.

**The frontmatter: a gap, found in 9.6b, nothing built.** *What the core reads from a doc:* only its title, the first `# heading` after the frontmatter (`crates/vnoc/src/userdata/read.rs`, `title_of`, used by `docs_of`). The frontmatter V-NOC writes is two lines, `node: <id>` and `hint: <path>::<qualname>` (`userdata/mod.rs`). **Nothing reads either one:** a doc belongs to the node whose folder it is in (`.vnoc/nodes/<shard>/<id>/`, with `node.toml`), the design says the folder wins if `node:` disagrees and that `hint:` is never used to find anything (`04-storage/01-vnoc-folder.md` §3), and no code compares them. So *changing or deleting a frontmatter line cannot detach a doc*, and there is no ID question to ask. *What a frontmatter edit can do:* (1) `title_of` strips the frontmatter only when the text starts with `---\n` and has a later `\n---\n`; a damaged fence (or a CRLF file, which never matched) leaves it in, and the first line that starts with `# ` anywhere, a YAML comment in the frontmatter, becomes the title in the doc list and the panel's selector (display only; the file name never changes). (2) Deleting the `# heading` makes the title the file name. (3) `20-search.md` plans to index `title:` and the body without the frontmatter, so once search exists a frontmatter edit changes what search finds. **Proposal, for you to decide:** do nothing now (the cost of a wrong frontmatter is a wrong title); if you want a guard, the same kind as 9.5b's, a pure function in `shared/` ("does this text drop or change `node:`") and a modal in the row that writes, "This changes the doc's `node:` line. V-NOC finds the doc by its folder, so it stays attached; the line is only a note", which I would not build, because it would ask about something that does no harm. The one thing worth a check is a title that is not the heading: show the title the core will read next to Save, which is a UI question and not a safety one.

## 9. What is not part of this

- The live view of §3. If users ask for it, it gets its own plan, and S5 is run for it then.
- Outlines, call trees, syntax errors or badges of unsaved text (E2).
- Formatting on save, completions, go to definition inside the card: Monaco in the webview has no language server. "Open in Editor" is the way.
- Undo after a save from the card: it is VS Code's undo, in a tab of that file.
- Native Save / Don't Save on close needs the canvas as a custom editor: its own plan, later.
